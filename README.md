# PAIMANA-AI

**Predictive Infrastructure Monitoring & Early Warning System**

Smart India Hackathon 2026 — Problem Statement **SIH26103**

---

## 1. Problem overview

PAIMANA monitors large Central Sector infrastructure projects. As of April 2026 the
national portfolio stands at roughly:

| National PAIMANA reference statistics — April 2026 | |
|---|---|
| Projects | 1,981 |
| Original approved cost | ~ ₹37.13 lakh crore |
| Revised cost | ~ ₹42.78 lakh crore |
| Cumulative expenditure | ~ ₹20.36 lakh crore |
| Ministries | 17 |
| Sectors | 22 |

*Source: SIH problem statement SIH26103. These are national reference figures. They are
**not** computed from the dataset loaded in this application, and the application never
presents its own project count as the national portfolio.*

The gap between original and revised cost is roughly ₹5.65 lakh crore. Conventional
monitoring reports cost variance and schedule delay **after** they have happened. The
problem statement asks two things:

1. Can overruns be flagged earlier, from leading indicators?
2. Does AI/ML actually give a significant gain over conventional statistical methods, or
   is the added complexity unjustified?

## 2. Solution overview

PAIMANA-AI is a web-based monitoring platform that:

- ingests either a synthetic demo dataset or a real PAIMANA CSV/XLSX extract;
- computes a transparent, component-wise risk score per project;
- explains each score with ranked risk drivers;
- raises early warnings carrying a **derived** financial impact estimate;
- benchmarks a **conventional statistical baseline against a machine learning model** on
  an identical train/test split, and reports the measured difference honestly — including
  where ML loses;
- answers free-form questions through an LLM assistant grounded strictly in the loaded
  dataset.

### Design commitment

Nothing in this system is fabricated. Model metrics are computed at runtime. Financial
impact figures state the arithmetic formula used. Fields absent from an imported file stay
absent and render as "Not available" or "Risk analysis pending". No output is presented as
an official Government of India prediction.

## 3. Architecture

```
PAIMANA / Imported Data
        ↓
Data Validation              (column mapping, type coercion, no imputation)
        ↓
Feature Engineering          (leading indicators only; leakage control)
        ↓
Statistical Baseline + ML Models
        ↓
Risk Prediction              (component-wise, degrades when inputs are missing)
        ↓
Explainability               (risk drivers, feature importance, SHAP)
        ↓
Early Warning                (with derived financial impact)
        ↓
Dashboard / AI Assistant
```

## 4. Technology stack

**Frontend** — React, Vite, Tailwind CSS, Recharts, Lucide

**Backend** — FastAPI, Python 3.10+, Pydantic v2, Uvicorn

**ML** — scikit-learn (Logistic Regression, Linear Regression, Random Forest), XGBoost,
SHAP

**LLM** — Google Gemini via the `google-genai` SDK (optional)

**Data storage** — JSON files on disk. There is no database server. The demo dataset lives
at `backend/app/data/projects_demo.json`; an imported dataset is persisted to
`backend/app/data/imported_dataset.json` and the active mode to
`datasource_state.json`, which is how a browser refresh or backend restart keeps the
imported dataset active. A production-ready PostgreSQL DDL schema is shown on the Settings
page as a migration target, but it is not currently wired up.

## 5. Demo data

The demo dataset contains **500 synthetic projects** generated by
`backend/app/data/generator.py`, calibrated against official MoSPI Infrastructure and
Project Monitoring Division (IPMD) Flash Report statistics across 13 Central Ministries.
Each project includes a **24-month longitudinal panel history** simulating realistic monthly
reporting periods with S-curve progress, gradual timeline slippage, and sticky MoSPI delay
causes (land acquisition, clearances, contractor issues, fund flow).

A detailed variable classification and MoSPI calibration dictionary is available in
[`DATA_SOURCES.md`](DATA_SOURCES.md).

For offline ingestion of real MoSPI IPMD Flash Reports from XLSX/CSV format:
```bash
cd backend
python scripts/fetch_flash_report.py --input path/to/flash_report.xlsx --output data/real_flash_report.csv
```

To regenerate the 24-month panel demo dataset:

```bash
cd backend
python -m app.data.generator
```

## 6. Real PAIMANA data import

Upload a `.csv`, `.xlsx` or `.xls` file from **Settings & Architecture → Real PAIMANA Data
Import**, or `POST /datasource/import`.

Column headers are matched case-insensitively against a table of known aliases (for
example `Original Approved Cost`, `Sanctioned Cost` and `Original Cost` all map to
`original_cost`). Only a project identifier column and a project name column are required.
Unrecognised columns are ignored and reported.

After import the UI shows a **field coverage table**: for every canonical field, which
source column it was mapped from and what fraction of rows actually carry a value. This is
how you can see that a field is missing rather than silently defaulted.

Derived fields are computed only where their inputs exist. `cost_variance_pct` requires
both original and revised cost. `schedule_delay_months`, if not supplied directly, is
derived from the two completion dates — and stays `null` if either is absent.

## 7. Data source distinction

The application keeps two datasets strictly separate, selected from the data source
dropdown in the navigation bar:

| | Demo Data — Synthetic | Real PAIMANA Data — Imported |
|---|---|---|
| Projects | 500 generated | However many rows were imported |
| Candidate variables | Present | Absent (never fabricated) |
| Risk scoring | Full | Only where required fields exist |
| Label | "Demo data is synthetic..." | "Imported PAIMANA data..." |

When **Real Data** is active, no synthetic project, value or risk score is shown. Missing
fields are not filled in. If a project lacks the inputs for a risk component, that
component is **excluded from the weighted composite** rather than counted as zero; if too
little of the total weight is computable, no score is produced at all and the UI shows
**"Risk analysis pending"**.

There is a third, separate concept: **imported PAIMANA data vs PAIMANA-AI derived
predictions**. Cost, schedule, progress and milestone values come from the dataset. Risk
scores, risk drivers, early warnings and financial impact estimates are produced by
PAIMANA-AI's prototype engine. The UI, the print report and the LLM system prompt all draw
this distinction explicitly.

## 8. Conventional vs ML evaluation

Open **CUF & Model Evaluation** in the sidebar, or call `GET /cuf/baseline-vs-ml`.

### Protocol

Both models share the same dataset, the same target, the same single stratified 80/20
hold-out split (`random_state=42`), and the same `StandardScaler`-preprocessed feature
matrix fitted on the training split only. **Only the estimator differs.**

### Leakage control

The classification target is defined as *cost variance ≥ 10% OR schedule delay ≥ 6 months
OR progress gap ≥ 10%*. Those three fields — and everything derived from them
(`cost_variance`, `expenditure_ratio`, `milestone_delay_ratio`, `status`, the revised
completion date, and others) — are **excluded from the feature matrix**. Feeding them in
would make the label a near-deterministic function of the inputs and produce meaningless
99% accuracy. The models see only leading indicators.

The excluded field list is displayed in the UI, struck through, so a reviewer can verify it.

### Models

| Task | Conventional baseline | ML model |
|---|---|---|
| Classification | Logistic Regression | XGBoost (falls back to Random Forest if `xgboost` is not installed) |
| Regression | Linear Regression | XGBoost / Random Forest |
| Regression reference | Historical average (training mean) | — |

### Measured results

All metrics are computed at request time from the active dataset. Nothing is hard-coded,
and the UI displays whatever the evaluation produces. The figures below were measured on
the 500-project demo dataset (400 train / 100 test, 38 features) in an environment where
**XGBoost was not installed**, so Random Forest was used. Your run will differ if XGBoost
is available — which is the point.

**Classification** (higher is better)

| Metric | Logistic Regression | ML model | Difference |
|---|---|---|---|
| Accuracy | 0.7800 | 0.8400 | +0.0600 |
| Precision | 0.8367 | 0.8545 | +0.0178 |
| Recall | 0.7455 | 0.8545 | +0.1090 |
| F1 Score | 0.7885 | 0.8545 | +0.0660 |
| ROC-AUC | 0.8901 | 0.9160 | +0.0259 |

**Regression** (lower is better for MAE/RMSE, higher for R²)

| Metric | Linear Regression | ML model | Difference |
|---|---|---|---|
| MAE | 5.7047 | 5.4891 | −0.2156 |
| RMSE | 8.4973 | 8.6502 | **+0.1529** |
| R² | 0.7186 | 0.7084 | **−0.0102** |

Historical-average reference: R² −0.0002.

**Interpretation.** Performance comparison is based on the same evaluation dataset and
test split. ML shows a consistent gain on the classification task, most clearly on recall.
On the regression task the result is mixed: ML edges out the baseline on MAE but is
**worse** on RMSE and R², meaning Linear Regression handles the larger errors better here.
That is reported as measured. **No model is designated a winner.**

A secondary study (`GET /cuf/comparison`) compares CUF variables against CUF + candidate
variables. It carries an explicit methodological caveat: it compares *feature sets*, not
methodologies, and it does include lagging variables, so its absolute metrics are
optimistic and should not be quoted as forecasting accuracy.

## 9. Environment setup

### Backend

```bash
cd backend
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # then edit .env
python run_backend.py
```

The API serves on `http://127.0.0.1:8000`; interactive docs at `/docs`.

`xgboost` and `shap` are optional. Without them the system runs, substitutes Random Forest,
and says so in the UI rather than mislabelling the model.

### Frontend

```bash
cd frontend
npm install
npm run dev                        # http://localhost:5173
npm run build                      # production build
```

To point the frontend at a different backend, set `VITE_API_BASE` in `frontend/.env`:

```
VITE_API_BASE=http://127.0.0.1:8000
```

## 10. Gemini configuration

The assistant works in two modes and never crashes if the LLM is unconfigured.

Create `backend/.env`:

```
GEMINI_API_KEY=your_key_here
# GEMINI_MODEL=gemini-2.5-flash    # optional override
```

Get a key from <https://aistudio.google.com/apikey>.

| Condition | Behaviour | UI shows |
|---|---|---|
| Key set, `google-genai` installed | Free-form questions answered by Gemini | "AI Assistant — Gemini LLM" |
| Key absent, SDK missing, or a call fails | Deterministic rule-based assistant | "LLM mode unavailable — using local assistant fallback." |

**The key is read only by the backend.** It is loaded from `backend/.env` via
`python-dotenv`, never sent to the browser, never included in any response body, and never
referenced in frontend source. `.env` is gitignored. Do not commit a real key.

### Hallucination control

The system prompt in `backend/app/llm/gemini_client.py` instructs the model to use only the
supplied PAIMANA-AI context; never invent project values or official government statistics;
reply exactly *"The available dataset does not contain this information."* when something is
missing; distinguish imported data from AI-generated analysis; never claim PAIMANA-AI
outputs are official Government predictions; not fabricate milestone, progress or contractor
information; and not assert causes of delay that the context does not evidence.

Context is assembled by `backend/app/llm/context_builder.py` from the **active** dataset —
a structured project record when one is identified, plus portfolio aggregates and the most
relevant projects for the question. Genuinely absent fields are passed as the literal string
`"Not available"` so the model sees the gap explicitly.

Example questions: *"Which sectors have the highest cost variance?"*, *"Why is this project
considered high risk?"*, *"Which projects require attention?"*, *"How many projects are
delayed?"*, *"What information is missing for risk prediction?"*

## 12. Early warnings and financial impact

Every alert carries: risk type, project, risk score, primary driver, financial impact,
recommended action, and model availability/confidence.

Financial impact is shown **only** when it follows arithmetically from fields present on
the project. Each figure is tagged *Derived estimate* and states its formula:

| Alert | Figure | Formula |
|---|---|---|
| Cost Overrun Risk | Projected additional cost | Revised Cost − Original Cost |
| Schedule Overrun Risk | Unexecuted balance exposed to delay | Revised Cost − Expenditure |
| Significant Progress Gap | Value of physical work shortfall | Progress Gap % × Revised Cost |
| Milestone Delay | *Financial impact: Not available* | No documented arithmetic basis |

These are derived quantities, not forecasts of future spending, and the UI says so.

## 13. Print / export

The Executive Dashboard has a **Print / Export Report** button (`window.print()`). The print
stylesheet in `src/index.css` hides the navigation, sidebar, banner and interactive
controls; converts the dark theme to a legible light layout; unlocks scroll containers so
nothing is clipped; and preserves the KPI cards, Recharts SVG charts and project tables.

The printed report adds a header with the title *PAIMANA-AI Executive Monitoring Report*,
the generation timestamp, the active data source ("Data Source: Demo Data — Synthetic" or
"Data Source: Real PAIMANA Data — Imported"), the project count, and the full source and
analysis disclosures.

## 14. Limitations

**Honest constraints a reviewer should know about.**

1. **The demo dataset is synthetic.** It is generated, not sampled from reality. Absolute
   metric values reflect the generator's structure, not real-world predictability. The
   pipeline and the comparison methodology are the contribution; the numbers are
   illustrative.

2. **Candidate variables are not in the public PAIMANA dataset.** Contractor past
   performance, land acquisition delay in days, clearance stage, tender disputes, weather
   disruption days, material price escalation, labour availability and funding delay are
   *proposed* schema extensions. They exist only in the synthetic data. They are not claimed
   to be captured in live Government systems today. On imported real data these fields are
   absent and are never fabricated.

3. **Consequently, ML on imported real data will be weaker.** The leading indicators that
   drive the model's advantage are exactly the fields a public extract usually lacks. The
   evaluation endpoint requires at least 30 projects and refuses to report metrics below
   that threshold rather than producing unstable numbers.

4. **Milestone data is rarely available publicly.** Milestone count, completions and delays
   are typically absent from published PAIMANA extracts, so the milestone risk component is
   usually excluded on real data.

5. **ML vs. Rule Engine Gap resolved via Option A.** The 0–100 composite score remains a
   transparent, deterministic rule-engine score (cost 28%, schedule 32%, progress 22%,
   milestone 18%). Alongside it, the trained ML model's predicted probability of critical
   delay (0–100%) and local SHAP feature attributions are surfaced directly, clearly
   disclosing the methodological distinction between rule-based monitoring and learned
   pattern recognition.

6. **No authentication or authorisation.** The login screen is a prototype shell backed by
   `localStorage`. There is no user store or session management. CORS is restricted to
   allowlisted origins via the `ALLOWED_ORIGINS` environment variable (defaults to
   `http://localhost:5173,http://127.0.0.1:5173`).

7. **No database.** State is JSON on disk and single-process. Concurrent writes are not
   handled. The PostgreSQL schema on the Settings page is a migration target only.

8. **Financial impact figures are arithmetic, not predictive.** They restate what the data
   already says (cost already revised, balance not yet spent). They are not a model forecast
   of future overrun.

9. **The LLM is constrained but not infallible.** The system prompt forbids invention and
   the context supplies only real values, but no prompt guarantees a language model never
   errs. Verify any figure against the Project Explorer before acting on it.

10. **Metrics vary with environment.** Because evaluation runs at request time and XGBoost
    is optional, the model named in the UI and the metrics shown depend on what is installed.
    The UI always reports which model was actually used.
